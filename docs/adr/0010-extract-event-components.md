# Extract Shared Presentational Components for Events 2026+

ADR-0008's Frozen Snapshot rule now applies only to Events 2025 and earlier. Starting with Event 2026, Event pages render through shared presentational components — `TalkCard`, `PersonCard`, `TicketCard`, `PeopleGrid`, `VideoHero`, `ImageMosaic`, `EventNav`, `EventLayout` — instead of inlining their own markup for every roster entry and section. This **narrows ADR-0008**, which continues to govern Events 2025 and earlier unchanged.

ADR-0008's actual concern was never markup reuse — it was data ownership. A past Event's roster is finished: it appears on exactly one page and will never change again, so loading it from a Collection or a shared dataset would misrepresent it as live. That reasoning holds regardless of how the roster is rendered. Extracting `TalkCard` does not make a Speaker's name, company, or headshot live data; it only means two Events' pages can render a Speaker the same way without duplicating the grid markup that draws one. Presentational components are a visual concern, changing a card's layout, spacing, or hover state is the same kind of change as editing a CSS file, and carries none of the data-integrity hazard ADR-0008 was written to prevent. A future Event page still writes its own roster, ticket tiers, and schedule directly into its frontmatter; it just hands each record to a shared component instead of hand-rolling the grid around it.

The forcing function is that Events 2026 and later are not finished yet at the time their pages are built. `EventLayout` and `EventNav` in particular exist because an in-progress Event's chrome — the section nav, the hero treatment — is genuinely shared scaffolding across a still-changing page, not a one-time capture. Continuing to hand-roll that chrome per Event, as ADR-0008 required for frozen pages, would mean re-deriving the same layout decisions on every new Event page with no page left to check them against once launched. The Frozen Snapshot rule's "do not extract" instruction was calibrated for content that will never be touched again; a current or future Event does not meet that bar, and treating it as if it did was costing real duplication for no benefit.

This also resolves an asymmetry in the domain types. `Talk` currently inlines a `speaker` record shaped only for a Speaker (`src/shared/data/types.ts`), even though an Organizer's card needs nearly the same fields (name, image, affiliation, social links). `Speaker` and `Organizer` collapse into a single `Person` type carrying a `role` distinction where the render actually needs one; `PersonCard` renders a `Person`, and `PeopleGrid` lays out a list of them regardless of whether the list is a Speaker roster or an Organizer roster. `Talk`, `Ticket`, and `EventConfig` join `Person` in the shared types module (`src/shared/data/types.ts`), which is where a shape crosses more than one component's boundary — the same rule that already governs `Talk` and `Activity` there. This is a rendering-shape unification, not a data-source change: a 2026+ page still declares its own `Person` and `Talk` records inline in frontmatter, the same as a 2025-and-earlier page does under ADR-0008; only the component and type that consumes them is now shared.

**Alternatives considered.** Extending ADR-0008's no-extraction rule to all future Events was rejected: it was written against a body of Events that will never change, and applying it to Events still being assembled would force real duplication of layout code (`EventNav`, `EventLayout`) with no snapshot-integrity benefit to show for it. Keeping `Speaker` and `Organizer` as separate types and writing two near-identical card components was rejected for the same reason ADR-0008 rejects coupling snapshots to a shared component in the other direction: two components that render the same fields invite drift, and the fields genuinely are the same fields.

## Consequences

Events 2025 and earlier are unaffected: their pages remain frozen snapshots exactly as ADR-0008 describes, with no migration to the new components and no change to their inlined markup. A 2025-or-earlier page must not be retrofitted onto `TalkCard`, `PersonCard`, or the other shared components introduced here — doing so would couple a finished snapshot to code that changes for other Events, which is precisely what ADR-0008 forbids.

Events 2026 and later still own their data: a Talk's abstract, a Person's headshot, a Ticket's price all live in that Event page's frontmatter, not in a Collection or `src/shared/data/*.json`. Only the rendering — the card, the grid, the nav, the layout — is shared. A future breaking change to `PersonCard`'s markup is a visual change reviewed like any other component change; it is not expected to be reviewed for data-integrity risk the way a change touching an Event's inlined roster would be.

`Speaker` and `Organizer` no longer exist as distinct types. Any code keying off that distinction (e.g. filtering a roster to "speakers only") must instead filter `Person` records by `role`. `Talk.speaker` moves from an inline record shaped like the old `Speaker` type to a reference into `Person`.
