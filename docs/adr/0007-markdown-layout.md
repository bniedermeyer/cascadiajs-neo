# Markdown Pages Are a Content Collection Rendered Through MarkdownLayout

Standalone markdown pages (welcome, code of conduct, mailing-list, etc.) live in a root-level `markdown` content collection, loaded by Astro's `glob` loader from `/markdown/` (a sibling of `src/`, not inside it) and schema-validated: `title` required; `description`, `image`, `showSponsors`, and `showTestimonials` optional; `width` of `"narrow" | "wide"`, defaulting to `"narrow"`. Routing is a single prerendered `src/pages/[...slug].astro` whose `getStaticPaths()` calls `getCollection("markdown")` and maps each entry's `id` straight to its URL slug — `welcome.md`'s `id` of `welcome` serves at exactly `/welcome`. No markdown page opts into anything; the collection's route is the only thing that renders markdown pages, and it renders every entry the collection contains.

`MarkdownLayout` is a faithful port of the legacy Enhance `simple-page.mjs` element. It wraps `Layout.astro` (the `main-layout` equivalent, which owns the document head, header, and footer) and adds the page chrome `simple-page` provided — a `#page` container, a `.page-title` bar (overcast-gray background, sound-navy heading), and a `.page-body` whose desktop width is controlled by `width` (`narrow` = 50%, default; `wide` = 70%). `[...slug].astro` calls `render(entry)` for a `Content` component and invokes `MarkdownLayout` directly with flat props — `title`, `description`, `width`, `showSponsors`, `showTestimonials` — read off `entry.data`, which the schema has already validated. `description` falls back to `title` when absent so authoring stays low-friction and meta tags never ship empty.

The port carries a single scoped `<style>` block. This is a deliberate, localized exception to Tailwind-first styling, and it is _permitted by_ — not a violation of — ADR-0003's exception clause: markdown-generated elements (`<a>`, `<li>`, `<img>`, and a `.toc` nav) are authored as plain markdown and therefore **cannot** receive utility classes. Styling them requires CSS selectors, which is exactly the case ADR-0003 reserves for `<style>`. Because Astro's scoping does not pierce slotted markdown content, the body-element rules use `:global(...)` under `.page-body`. A comment at the top of the block records why the exception lives here and must not be copied into ordinary components. The fidelity bar and its verification method are unchanged (ADR-0001, ADR-0004).

The routing file is a build-time allowlist, not the runtime catch-all this project forbids. `getStaticPaths()` runs at build time, enumerates the collection once, and emits a fixed, known set of static routes — there is no dynamic dispatch at request time and no fallback for slugs outside that set. This is categorically different from the legacy Enhance `$$`/`$` catch-all, which resolves arbitrary request paths against the filesystem at runtime. `[...slug].astro` uses Astro's rest-param syntax only so a future entry `id` containing a `/` (a nested page) still produces the correct route; it does not open routing to anything the collection doesn't already enumerate, and named routes like `index.astro` take precedence over it as always.

**Alternatives considered.** This layout was first built with markdown pages opting into `MarkdownLayout` via `layout:` frontmatter, where Astro supplied the layout a single nested `frontmatter` object holding all of a page's YAML keys. We moved to a content collection so page data is schema-validated at build time and content is decoupled from the routing layer; the flat-props layout interface (instead of the `frontmatter` wrapper) followed from the route invoking the layout directly. `image` is validated but intentionally not wired to `Layout`'s `ogImage` — the original `layout:` mechanism never forwarded it, so leaving it unused preserves prior behavior; wiring it up is a possible future change.
